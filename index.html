Hive Metastore to Unity Catalog: a step-by-step migration guide

Nine steps from inventory to HMS shutdown. Each step gives the action, the command, the gate to pass, and the failure modes seen in practice.

00

Choose your migration path

Decide the approach before touching data. The path sets how much data moves and how long the legacy and new worlds coexist.

PathHow it works
Recommended
Federate, then upgrade in place		Expose the Hive metastore as a foreign catalog in Unity Catalog, then upgrade the foreign tables in place. No data movement; history, permissions and views are preserved.
Alternative
Direct migration		SYNC for external tables, CLONE or CTAS for managed tables. Use UCX workflows rather than hand-written scripts for large estates.
Bulk tooling
UCX (Databricks Labs)		Assessment plus workflows for identities, permissions, storage locations and tables, with code migration and data reconciliation. UCX is a Labs project and is not directly supported by Databricks.
Assess→Plan→ Migrate→Validate→Decommission

Which method fits this table?

0.1 Downtime position

Attaching a Unity Catalog metastore does not require platform downtime: existing workloads keep using hive_metastore while tables and code move in phases. The outage risk sits in switching active writers and readers from old table references to the new objects, and in disabling Hive access before every consumer has moved. Avoid a big-bang migration unless the estate is small and fully understood.

ActivityExpected impactControl
Create or identify the UC metastoreNo planned workload outageTry it in a non-production workspace first
Attach the workspace to Unity CatalogHive workloads keep running during the transitionKeep hive_metastore available; check the workspace default catalog (see Step 2)
Federate the Hive metastoreLow-disruption bridge; no data movement for initial accessValidate permissions and namespace behaviour
SYNC external tablesUsually online; source stays availableSchedule repeat syncs during the transition
DEEP CLONE / CTAS of managed tablesCopy can run online but creates a new target tableFreeze or control source writes for the final cutover
Update jobs, notebooks, dashboards, appsConsumer-specificDeploy in waves; test before production
Disable Hive metastore accessIntentional breaking change for unmigrated consumersOnly after exit criteria are met (Step 8)

0.3 Assumptions to confirm and migration controls

  • The target region has a UC metastore, and account-level users, groups and service principals exist.
  • Catalog and schema design is agreed; storage credentials and external locations are available for external tables.
  • Critical jobs and downstream consumers have named owners.
  • Original Hive tables are preserved until validation and rollback windows expire.
  • History, permissions, views and non-Delta formats are validated explicitly, because behaviour differs by method.
  • A migration tracker exists with one row per table, view, job, dashboard and application (template in the appendix).
  • A change window is set for each wave, with a freeze on unplanned schema and permission changes during cutover.
  • Incident escalation contacts and rollback authority are named.
  • The current Hive state (definitions, locations, owners, grants, dependencies) is captured, and backup, retention and recovery for source data are confirmed.
01

Assess the estate

Inventory first. Migrate only what is alive.

1.1 Install UCX and run the assessment

databricks labs install ucx
databricks labs ucx ensure-assessment-run
  • Prerequisites: Databricks CLI v0.213+, Python 3.10+, account admin and workspace admin roles. UCX cannot be installed as a service principal.
  • The installer asks for the workspace CLI profile (the config file must also hold a profile for the parent account), an inventory database name (default ucx), a SQL warehouse, and which workspace-local groups to migrate.
  • Results land in Delta tables in the inventory database and populate the assessment dashboard.

1.2 Inventory what to move

  • Groups, external locations and mount points, tables and views, functions, workflows, notebooks.
  • Use the UCX readiness score as the baseline for tracking progress.
  • Per table: format, size, partitioning, last read and last write, managed or external, Delta history and retention needs, and the table location.
  • Per consumer: readers and writers by job, notebook, dashboard, API or application; hard-coded paths and two-level table names; Hive-specific SQL such as MSCK, ALTER TABLE ... PARTITION and LOCATION; streaming checkpoints and state locations; downstream extracts and reverse-ETL processes.
  • Governance: legacy ACLs, workspace-local groups, and PII, confidential, regulatory or residency-sensitive data.

Classify every object:

ClassMeaning
Migrate nowActive, business-critical and technically ready
Remediate firstActive but blocked by permissions, format, code or storage issues
RetireUnused, duplicate or superseded
DeferLow risk, with a named owner and a later migration wave

1.3 De-scope dead weight with system tables and lineage

Query usage and lineage to find inactive jobs and unused tables. One public case study de-scoped roughly 40% of jobs this way, which shrank the migration and the validation burden.

-- Tables with no reads in the last 90 days (adapt to your system-table access)
SELECT source_table_full_name, MAX(event_time) AS last_read
FROM system.access.table_lineage
WHERE source_table_full_name LIKE 'hive_metastore.%'
GROUP BY 1
HAVING MAX(event_time) < current_date() - INTERVAL 90 DAYS;
Evidence, not proofLineage only records reads on compute that captures it, and only for the system-table retention period. A table with no lineage rows at all will not appear in the query above. Left-join the result to the UCX table inventory so never-seen tables are reviewed with their owners, not silently dropped.
02

Design the Unity Catalog target

Hive has two levels (schema.table). Unity Catalog has three (catalog.schema.table). The mapping is the main design decision.

  • Metastore exists, is attached to the workspace, and the regional layout is agreed.
  • Catalog strategy chosen (by environment, business domain, or both) and documented.
  • Schema mapping reviewed, e.g. hive_metastore.sales to prod.sales.
  • Group ownership chosen for catalogs and schemas (not individual users).
  • Managed versus external table strategy, storage locations and external locations decided.
  • Catalog-to-workspace bindings, service principal access, and dev / test / prod separation decided.
  • Cross-workspace and cross-region sharing requirements noted.

Naming model and baseline grants

Use one consistent pattern, for example <domain>_<environment>.<schema>.<table> such as finance_prod.core.customer or risk_prod.transactions.alerts. Create the targets and baseline grants for groups, not individuals:

CREATE CATALOG IF NOT EXISTS finance_prod;
CREATE SCHEMA  IF NOT EXISTS finance_prod.core;
GRANT USE CATALOG ON CATALOG finance_prod TO `finance-data-users`;
GRANT USE SCHEMA  ON SCHEMA  finance_prod.core TO `finance-data-users`;
GRANT SELECT      ON SCHEMA  finance_prod.core TO `finance-data-users`;
Default catalogOn a workspace where UC was enabled automatically, the workspace catalog is the default catalog. On a manually enabled workspace, hive_metastore is the default, so unqualified two-level names keep resolving to Hive until you change it. Keep hive_metastore as the default while migrating, unless you have fully migrated off Hive, and use three-level names in migrated code.

Generate and review the table mapping

databricks labs ucx create-table-mapping
# Edit the generated CSV: each Hive table -> target catalog, schema, table
databricks labs ucx create-catalogs-schemas   # optional: create the targets
TipTreat the mapping CSV as a reviewed, version-controlled artifact. It drives every later table step.
03

Prepare identity and storage

Unity Catalog governs by account-level groups and external locations. Both must exist before tables can move.

3.1 Identity: workspace groups to account groups

  • Grant access to account-level users and groups, never to workspace-local groups.
  • Provision users, groups and service principals at the account level first (typically SCIM sync from your identity provider), then map legacy principals to target groups and define ownership groups for catalogs, schemas, tables, volumes and external locations.
  • UCX provides a group migration workflow that upgrades membership to account-level groups and migrates permissions.

The group migration workflow depends on the assessment output, also removes unnecessary workspace groups and permissions, and can be run multiple times until every group and permission is handled. Run it from the UCX-generated README notebook. Command-level detail is in the UCX group migration reference.

3.2 Storage: credentials and external locations

databricks labs ucx create-uber-principal   # read-only SP over all table storage; used by workflow compute
databricks labs ucx principal-prefix-access # optional: discover storage accounts and credentials in use
databricks labs ucx migrate-credentials     # optional: create UC storage credentials
databricks labs ucx migrate-locations       # optional: create UC external locations from the assessment
Clean upDeprovision the uber principal when the upgrade is finished.

3.3 Mounts and DBFS files to external locations and volumes

  1. Create an external location for the cloud path the mount points to.
  2. Create an external volume on a subpath.
  3. Copy files that live in DBFS root (files already in mounted cloud storage are reached through the location).
  4. Verify reads, then unmount.
USE CATALOG main;
USE SCHEMA data;
CREATE EXTERNAL VOLUME IF NOT EXISTS raw_files
  LOCATION 'my_data_loc/csv-files/';
dbutils.fs.cp("dbfs:/FileStore/tables/data.csv",
              "/Volumes/main/data/raw_files/data.csv")
dbutils.fs.ls("/Volumes/main/data/raw_files/")   # verify
dbutils.fs.unmount("/mnt/oldpath")               # after jobs are repointed
  • Use workspace files, not volumes, for code, libraries and small files in DBFS root.
  • Jobs that read or write via mount paths must switch to /Volumes/... paths.
  • For large copies use the CLI fs cp or a distributed Spark copy.

4.1 External tables with SYNC

SYNC is metadata-only, works per table or per schema, writes bookkeeping properties back to the Hive table, and can be re-run to pick up source changes, which supports a gradual hybrid transition. The upgrade wizard wraps SYNC in Catalog Explorer (external tables only, can be scheduled) and needs a storage credential, an external location and CREATE EXTERNAL TABLE.

-- Dry run first
SYNC TABLE main.sales.orders FROM hive_metastore.sales.orders DRY RUN;
SYNC SCHEMA main.sales FROM hive_metastore.sales SET OWNER `data-owners`;

-- Hive managed table stored outside workspace storage: AS EXTERNAL is required
SYNC TABLE main.sales.events AS EXTERNAL FROM hive_metastore.sales.events;

Read the status code in the result: SUCCESS and DRY_RUN_SUCCESS are good; NOT_EXTERNAL means a managed table needs AS EXTERNAL; DBFS_ROOT_LOCATION means use DEEP CLONE; HIVE_SERDE means convert to Delta first; TABLE_ALREADY_EXISTS is a target name clash. External table paths must not overlap, or sit under managed storage. Schedule repeat SYNC runs while the source is still written, and agree the final sync point for cutover.

4.2 Hive SerDe tables

SerDe tables fail with UPGRADE_NOT_SUPPORTED.HIVE_SERDE. Convert first:

CONVERT TO DELTA hive_metastore.sales.orders;
SYNC TABLE main.sales.orders FROM hive_metastore.sales.orders;

4.3 Managed tables with DEEP CLONE

Clone is almost always preferred over CTAS. It needs managed Delta tables and must be a deep clone from Hive to UC.

CREATE OR REPLACE TABLE main.sales.customers
DEEP CLONE hive_metastore.sales.customers;
  • A deep clone creates a new table. It does not preserve source history, so confirm whether consumers need time travel before choosing it.
  • For actively written tables, run a final reconciliation after the last source write.
  • Do not delete the Hive source until the rollback window has expired.
Shallow clonesDo not drop the old Hive table if a shallow clone was used.

4.4 Federated route: upgrade foreign tables in place

  1. Create a connection to the Hive metastore (for the legacy internal metastore, federation handles authorization; for an external one you need host, port, database, credentials and CREATE CONNECTION).
  2. Create a storage credential and external location for the registered table paths.
  3. Create a foreign catalog on the connection (the docs call the one mirroring the internal metastore hms_in_uc).
  4. Grant privileges on the foreign catalog (row and column filters are available).
  5. Point workloads at it with USE CATALOG hms_in_uc or by setting it as the compute default catalog.

Federation supports managed and external tables, schemas, views and Hive SerDe tables. It does not expose Hive functions and UDFs or JDBC-backed tables, so recreate functions in Unity Catalog by hand. Supported compute is SQL warehouses, serverless, and standard or dedicated access mode on DBR 13.3 LTS, 14.3 LTS and 15.1+; no-isolation clusters are excluded. Fallback mode lets a workload use cluster- or notebook-scoped credentials when a UC permission check fails; it is meant only for the migration period.

Rules for the bridge period: keep source Hive tables intact; use fully qualified names; allow no new production dependencies on Hive-only objects; record all reads and writes to the source tables; agree a maximum bridge duration; and monitor permission differences between legacy ACLs and UC grants. Joins that mix hive_metastore data across workspaces fail.

ALTER TABLE hms_in_uc.sales.orders SET MANAGED MOVE;  -- to UC managed; disables the source table (recommended)
ALTER TABLE hms_in_uc.sales.orders SET MANAGED COPY;  -- to UC managed; source stays accessible
ALTER TABLE hms_in_uc.sales.orders SET EXTERNAL;      -- to UC external (supports DRY RUN)
ALTER CATALOG hms_in_uc DROP CONNECTION;              -- after migration
  • SET MANAGED needs DBR 17.3 LTS or above, or serverless compute, and a foreign table federated from a Hive metastore or AWS Glue. It was announced as Public Preview in November 2025; the current docs mark the Catalog Explorer conversion as Beta, so confirm the status of the SQL path before relying on it.
  • Privileges for a foreign table: OWNER or MANAGE on the table, plus CREATE on the external location. Tables using column mapping with minReaderVersion=2 and minWriterVersion=7 fail conversion. After conversion, readers and writers need DBR 15.4 LTS or above.
  • Managed tables unlock predictive optimization (automatic compaction, clustering, vacuuming). The in-place upgrade preserves history, configuration, permissions and views.
  • DRY RUN is documented for SET EXTERNAL only. A syntax check against a current workspace (October 2026) accepted SET MANAGED, SET MANAGED MOVE, SET MANAGED COPY, SET EXTERNAL, SET EXTERNAL DRY RUN and UNSET MANAGED, and rejected SET MANAGED ... DRY RUN with PARSE_SYNTAX_ERROR.
  • To convert a whole schema or catalog, iterate over the tables, or use the Labs project discoverx:
(dx.from_tables("hms_in_uc.*.*")
   .with_sql("ALTER TABLE {full_table_name} SET MANAGED MOVE;")
   .apply())
Rehearse firstRehearse with SET MANAGED COPY on a non-critical table if rollback matters, and read the "Foreign tables using SQL" section of the convert-to-managed docs before running MOVE.

Access through an external Hive metastore (or AWS Glue) is read-only; the internal workspace metastore is read-write.

4.5 Views and functions

Recreate views after all referenced tables are migrated, rewriting references to three-level names. Recreate functions in the target catalog. Update every reference to hive_metastore.schema.table, two-level schema.table names, hard-coded cloud storage paths, and workspace-local functions or temporary objects.

4.6 Run the UCX table migration workflow

Run from the README notebook or Jobs & Pipelines after the preparatory tasks in Step 3. External Hive tables are upgraded with SYNC; managed DBFS-root tables with DEEP CLONE. Hive managed tables must be Delta or Parquet. Expect to run it more than once.

Each task writes its output to Delta tables in the inventory database chosen at install time, so query those tables to track which tables have migrated. Rerun the workflow until all are upgraded. Further commands and options are in the UCX table migration commands and table migration workflows references. UCX code migration is documented as still under development, so scan and fix code with the checks in Step 6.

05

Migrate permissions

Re-express Hive ACLs as Unity Catalog grants for account groups.

  1. Extract Hive ACLs and group memberships.
  2. Map each to an account-level group.
  3. Apply grants through automation (UCX or scripts), not by hand.
  4. Set table owners; the upgrade wizard recommends group ownership.
  5. Validate access parity: sample users from each group must see the same data as before.
  6. Re-create row filters and column masks that exist as dynamic views or Hive-era workarounds, and give job service principals their own grants.
  7. Snapshot Hive ACLs and SHOW GRANTS output before revoking anything, so access can be restored.
GRANT USE CATALOG ON CATALOG main TO `analysts`;
GRANT USE SCHEMA, SELECT ON SCHEMA main.sales TO `analysts`;
SHOW GRANTS ON TABLE main.sales.orders;

Consumers to remediate and test

Jobs and workflows; notebooks and SQL queries; Structured Streaming pipelines; Delta Live Tables / Lakeflow pipelines; SQL dashboards and alerts; BI tools and JDBC/ODBC clients; APIs and application services; data extracts and downstream platforms; data quality checks.

  • Missing USE CATALOG / USE SCHEMA privileges.
  • Direct filesystem or storage access that bypasses Unity Catalog.
  • Hive-specific partition commands and implicit default-catalog assumptions.
  • Temporary views that hide unresolved two-level table references.
  • Streaming checkpoint compatibility; plan a dedicated streaming cutover.
  • SQL warehouse versus cluster behaviour; service principal authentication and permissions.
07

Validate and run in parallel

Prove equivalence before anyone switches over.

  • Row counts and checksums match for every migrated table.
  • Distinct business keys, null counts on critical columns, min / max timestamps, partition coverage, and totals for critical measures match.
  • Duplicate and referential-integrity checks pass; latest source and target timestamps agree.
  • Schemas, data types, comments, constraints, partitioning and table properties match.
  • Old and new pipelines run in parallel; historical and incremental loads reconcile.
  • Dashboards and BI connections repointed and compared.
  • Access-parity tests pass per group.

Security validation

  • Unauthorised users cannot see the catalog, schema, table or sensitive columns; intended groups keep the access they need.
  • Row filters and column masks behave as designed.
  • External locations do not grant broader cloud-storage access than intended.
  • Audit events and lineage are visible; workspace-catalog bindings block unintended cross-environment access.

Workload validation

Run representative workloads in a production-like environment and compare functional output, runtime and cost, query plans, streaming latency and checkpoint progress, dashboard refreshes, job retries and failure rates, data quality alerts, and downstream delivery timings.

Reconciliation queries

SELECT 'hive' AS src, COUNT(*) AS n FROM hive_metastore.sales.orders
UNION ALL
SELECT 'uc',   COUNT(*)        FROM main.sales.orders;

-- Cheap content check: run both directions

  SELECT * FROM hive_metastore.sales.orders EXCEPT ALL SELECT * FROM main.sales.orders)

  SELECT * FROM main.sales.orders EXCEPT ALL SELECT * FROM hive_metastore.sales.orders);

08

Cutover and decommission

Retire the legacy path deliberately, with a way to see who still uses it.

  1. Deprecation notice. Optionally add a comment on the old Hive table; queries then show a warning.
  2. Watch fallback use. Fallback mode on external locations lets unmigrated workloads keep working during federation. Check the audit log, then turn it off.
  3. Make UC the default. Set the federated (or target) catalog as the workspace default catalog. On a single cluster, set spark.databricks.sql.initial.catalog.namespace to a UC catalog.
  4. Block bypass. Use compute policies and Enforce user isolation to block clusters that skip table access control.
  5. Disable direct HMS access. Compute connects to the Hive metastore by default until you disable it. Workspace-wide: Workspace admin > Security > Disable legacy access, set to "Disabled: legacy access features cannot be used", wait about five minutes, then restart all clusters. Per cluster, set the Spark configurations below.
  6. Drop old tables. First revoke access and re-run dependents to surface hidden dependencies.
-- Was fallback used in the last 30 days?
SELECT event_time, user_identity, action_name, request_params, response, identity_metadata
FROM system.access.audit
WHERE request_params.fallback_enabled = 'true'
  AND request_params.path LIKE '%some-path%'
  AND event_time >= current_date() - INTERVAL 30 DAYS
LIMIT 10;
spark.databricks.unityCatalogOnlyMode True
spark.databricks.sql.initial.catalog.namespace <uc-catalog-name>
Point of no returnAfter 30 days with legacy Hive access disabled, the workspace becomes Unity Catalog-only permanently and direct Hive access can no longer be re-enabled. Do not disable it until every table, job and consumer has moved, and all jobs run on DBR 13.3 LTS or above.

Per-wave cutover procedure

Migrate in waves, not all at once. For each wave:

  1. Announce the cutover start and the affected assets.
  2. Confirm there is no active incident or unresolved validation failure.
  3. Pause or drain source writers where duplicate writes are not supported.
  4. Run the final SYNC, final clone or in-place upgrade.
  5. Reconcile source and target data.
  6. Grant the target UC permissions.
  7. Deploy updated jobs, notebooks, dashboards and application configuration.
  8. Run smoke tests and business validation.
  9. Resume writers against the Unity Catalog object.
  10. Monitor for the agreed observation period.
  11. Mark the wave complete only after owner sign-off.
Go / no-goProceed only if critical data reconciliation passes, all critical consumers are tested, required grants are validated with representative identities, no P0 / P1 defects are open, rollback data and configuration are available, and business and technical owners approve the wave.

Operational rollback

If validation or production monitoring fails after a wave:

  1. Stop new writes to the target object if it is safe to do so.
  2. Revert jobs, notebooks, dashboards and application configuration to the Hive references.
  3. Resume source writers only after confirming source consistency.
  4. Compare source and target to find any writes made after cutover.
  5. Preserve the target table and logs for investigation; do not delete or overwrite the source until the incident review is complete.
  6. Record the failure, the corrective action and the revised cutover prerequisites.

Rollback is simple for read-only consumers. It needs explicit reconciliation when the target has accepted writes, so define writer ownership and reconciliation rules before cutover.

Rollback options by method

There is no single undo. What is reversible depends on the method used:

Method usedRollback
SYNC / upgrade wizardNon-destructive. The Hive table is left intact and both metastores point at the same storage. Drop the UC external table to back out. SYNC writes bookkeeping properties to the Hive table; the sources do not describe removing them.
DEEP CLONE / CTASNo undo command. The clone is a new table without pre-migration history. Keep the Hive source until the clone is validated, then drop the clone to back out.
SET MANAGEDRun UNSET MANAGED before dropping the managed table, within the documented 14-day rollback window. See below.
Access revoked on old tableRe-grant. The sources give no procedure, so snapshot SHOW GRANTS output first.
 
ALTER TABLE main.sales.orders UNSET MANAGED;  -- reverts the table to external
DROP TABLE  main.sales.orders;                -- re-federates it as a foreign table after the next catalog sync
Order mattersSkipping UNSET MANAGED before the drop risks data loss or inconsistency. For commits made between conversion and rollback, time travel works by version, not by timestamp. Seven days after rollback, Databricks deletes the data in the managed location.
Staged retirementRemove access first (reversible), watch for breakage, then purge the data a week or more later. Keep the Hive tables and data until the parallel run is signed off.
NoteDatabricks is progressively disabling direct Hive access for workspaces with no Hive metastore usage, starting July 2026 (per the disable-HMS doc). Confirm current behaviour for your workspace.

Finalisation

  • No active job, notebook, dashboard or application references hive_metastore; repositories and workspace objects are searched for two-level names and direct paths.
  • Service principals and external clients use Unity Catalog objects.
  • Temporary federation and SYNC schedules are removed.
  • Direct Hive access is disabled under the approved change plan.
  • Inventory, validation evidence, approvals and rollback records are archived.
  • Obsolete Hive tables are removed only after the agreed retention period and business approval.
  • Platform documentation, support procedures and onboarding materials are updated.

Source changes during copyFreeze writers, use repeated sync, or use an in-place upgrade path
Permission regressionTest with representative users and service principals
Different default-catalog behaviourUse fully qualified three-level names during migration
Streaming interruptionValidate checkpoints and run a dedicated streaming cutover
Loss of historical behaviourConfirm Delta history and time-travel needs before clone / CTAS
Direct storage access bypasses governanceReplace direct paths with volumes, tables or governed external locations
Cross-workspace access changesValidate workspace-catalog bindings and sharing requirements
Rollback unsafe after target writesDefine writer ownership and reconciliation rules before cutover

Recommended first wave

Start with a representative, low-risk domain: a small number of active tables, at least one external and one managed Delta table, one batch job and one dashboard, known owners, and no irreversible downstream writes. Use it to validate the catalog model, grants, tooling, reconciliation checks, deployment process, monitoring and rollback before scaling to critical domains.

Master checklist

Progress saves in this browser.

  • Roles, change windows, freeze and rollback authority agreed; migration tracker created.
  • UCX installed; assessment run; readiness score recorded.
  • Inactive jobs and tables de-scoped using system tables.
  • Table mapping CSV reviewed and committed.
  • Account groups created; workspace groups migrated.
  • Storage credentials and external locations created.
  • Mounts replaced by external locations and volumes.
  • External tables synced; SerDe tables converted.
  • Managed tables cloned; views recreated.
  • Permissions migrated; access parity validated.
